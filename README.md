# 基辅安全信息汇总

面向个人的中文移动端看板，汇总基辅市的空袭警报状态、按分组的轮流停电计划，以及基辅自来水公司官方发布的停水公告。界面上的乌克兰语公告、街道名与门牌均译为中文后展示，并保留官方原文链接供核对。同一套前端既作为 PWA 在浏览器中使用，也由 Capacitor 打包为 Android APK。

本仓库托管于 GitHub 账号 `ericljw98-crypto`。版本真源是根目录 `version.json`（当前 1.3.3），编译产物见 `dist/kyiv-live-debug.apk` 与 `dist/SHA256SUMS.txt`，同时可作为 GitHub Release 资产分发。默认数据来自同仓库 `snapshot` 分支的静态快照：手机只读这一个 HTTPS 地址，不连接本机或局域网服务，电脑关机也能打开页面；数据新鲜度由一台能访问上游的机器每 5 分钟推送保证，GitHub Actions 只是电脑离线时的兜底。预警数据与版本信息经同一份快照分发，袭击后果公开报道索引以 APK 内置的校订副本为准。

## 数据边界与采集范围

本应用采集的是**官方公开发布、用于提醒居民提前避险**的信息，共四类：区域级空袭警报状态与起止时间、红／黄级别、官方给出的威胁类型标签（例如「导弹威胁」「无人机威胁」「弹道导弹威胁」），以及供电公司与自来水公司官方发布的停电计划、停水公告。官方发布此类预警的目的正是让居民有时间前往掩蔽所、储水充电，本应用是把这些已公开的信息汇总成中文看板，不做二次判读。

不采集、也不显示非官方渠道传播的来袭目标坐标、飞行轨迹、速度、拦截动态、防空系统部署与打击后果。理由与信息性质有关，与使用者国籍无关：这类内容不属于官方避险预警，且可被用于校正后续打击，传播后果落在平民身上。因此数据源限定在官方公开渠道与转发官方区域级状态的公开聚合接口，不接入 Telegram 等平台上的实时军情频道。该采集范围固定写入代码与数据链路，不是可关闭的选项；不设「内部版」或私人分支。

本应用不是官方预警系统。避险决策以实体警报器、官方空袭警报应用（Air Alert）与地方政府通报为准。

## 袭击后果公开报道索引

主页的「袭击后果 · 公开报道索引」是**事后**信息模块，与预警模块性质不同：只收录袭击结束后已经公开发布的汇总数字——发射的导弹与无人机数量、人员伤亡、原文链接。发射数量只取单一信息源（新华社）最新一次通报，当前只保留一条校订记录，不并列其它来源或其它口径；「重点目标」单独列示，照录该来源原文点出的能源基础设施与变电站，没有公开数字时写「未公布」。数据存于 `data/aftermath.json`。

该模块不接入来袭坐标、航迹、速度、拦截动态与防空系统部署，不显示实时军情，也不参与警报判定；它不是实时预警，不能用于避险判断。通报口径可能不一致，引用数字一律以所引原文为准。

维护方式：运行 `npm run aftermath:candidates` 从公开新闻 RSS 生成候选清单 `data/aftermath-candidates.json`（只含标题、链接、发布时间与来源），再逐条打开原文，把核对过的日期、来源、口径、导弹数、无人机数、伤亡数、重点目标与原文链接写入 `data/aftermath.json`；`npm run snapshot:push` 也会把同一份索引写入快照。构建 APK 时 `scripts/sync-aftermath.mjs` 把它复制进 `www/aftermath.json`。客户端对快照先做单一来源、单条收敛，同日期条目以 APK 内置的校订副本覆盖（补齐重点目标等新增字段），快照完全没有该字段时直接用内置副本，因此线上旧快照不会让界面回到多来源并列的状态。自动抓取只负责找到报道，数字一律人工校订，未校订的条目不会进入索引。

## 中文展示

服务端 `server/zh.js` 是唯一的乌克兰语→中文词库真源，`scripts/sync-zh.js` 把它同步为 `www/zh.js`。公告标题优先使用人工校订译文，未命中的新公告走本地词库；公告正文不逐词直译，而是抽取中文要点，避免乌克兰语屈折变化与语序差异生成看似完整却失真的译文。所有译文都配有官方原文链接，点击公告标题即可核对；接口不回传未翻译的乌克兰语原文字段。

分类与区域筛选一律在翻译之前用乌克兰语原文完成，译文不参与任何判定，不会改变「本地址／本区／全市／其他区域」的结果。街道、片区、门牌与地址库查询结果同样译为中文；设置页可用中文街名查询，服务端在调用官方地址库前映射回官方原名。前端还设有一道显示兜底：任何仍含西里尔字母的字符串都会在渲染前被本地词库处理，界面不会出现未翻译的乌克兰语。词库是离线的，不调用外部翻译服务，公告原文不会外发。

## 界面结构

底部只有三个页签：**主页**在一个滚动页面内依次显示警报、电力、供水、袭击后果公开报道索引与避险说明五张卡片；**设置**配置停电分组、刷新间隔与浏览器通知，数据来源固定为 GitHub 静态快照、不可更改；**软件更新**显示当前版本、每次检查的结果、新版本说明与安装包下载入口。原先按卡片跳转的四个锚点标签已合并为主页，版本相关内容也从设置页移到软件更新页。避险卡片只保留避险提示，不再列出官方网站入口；页脚只显示快照生成时间与刷新信息，不再逐一点名官方站点。

主页上的按钮（顶部 ⟳、数据来源条的「刷新数据」、更新状态条的按钮）**一律只刷新数据**，不触发软件版本检查；软件更新只靠启动、切回前台与定时的自动检查提醒，手动查看与手动检查都在底部「软件更新」页。供水卡片只显示最新的 3 条公告，按发布时间倒序，没有日期的条目排在有日期的后面。

## 数据源

| 模块 | 来源 | 说明 |
| --- | --- | --- |
| 空袭警报 | Tryvoha 公开警报聚合接口（免密钥） | 区域级状态与威胁类型；配置 `ALERTS_UA_TOKEN` 后自动切换至 alerts.in.ua 官方接口 |
| 停电 | 供电公司公开接口（region 25 / dso 902） | 按分组的停电时段、紧急停电状态；快照内置全部分组供下拉选择 |
| 供水 | 基辅自来水公司官网 `/news`、`/shutoffs` | 公告与按地址列出的事故、计划停水；按关注区域筛选，标题译为中文，界面只显示最新 3 条 |

停水没有结构化的实时管网状态接口。官网在战时出于安全考虑不公开逐栋停水明细，具体门牌需拨打官方调度电话确认。区域筛选基于公告中的街道、片区与区名关键词，可能漏判，界面已标注该限制。所有数据源失败时显示「暂不可用」或缓存标记，不以推测状态冒充实时状态。

## 警报实时性与提醒

警报状态由上游接口聚合后写入静态快照，快照约每 5 分钟生成一次，页面每 60 秒重新读取，页脚与顶部状态条都会显示快照的生成时间与已过去时长，不把 5 分钟前的状态标成实时。页面切到后台时自动暂停刷新。浏览器通知只在警报生效或解除、且应用处于打开状态时提示，属于补充提醒，不替代官方预警。页面所有时间统一显示为基辅时间，按 EET/EEST 的固定夏令时规则自行换算，不调用 `Intl.DateTimeFormat` 的 `timeZone` 选项：部分 Android WebView 的 ICU 数据只有旧名 `Europe/Kiev`，传 `Europe/Kyiv` 会抛 `RangeError` 并中断整页渲染。

需要区分两类时间：**快照提供的事实**（警报状态、计划停电时段、公告发布时间、索引更新时间）一旦生成就固定，页面显示其生成时间与已过去时长；**「当前」类判断**（停电时间轴的当前时刻竖线、当前有电／停电中、距下次停电或恢复的倒计时、警报已持续时长）一律由客户端按设备此刻的基辅分钟实时重算，并每分钟随顶部时钟一起推进，不使用快照里冻结的 `now` 与 `kyiv.minute`。否则快照生成于上午、用户在傍晚打开时，竖线会停在上午的位置，倒计时也不会减少。若快照中的「今日」计划表日期与当前基辅日期不一致，则隐藏竖线并明确提示计划表待更新，不把旧计划表当作当日状态。供水公告的 `<time datetime>` 若不带时区，按官网标注的基辅墙上时间照录；带 `Z` 或偏移的 ISO 才换算为基辅时间。

可靠的即时推送应以官方空袭警报应用（Air Alert）、城市警报器与地方政府通报为准。本应用不接入 Telegram 等平台上实时分享来袭方向、坐标、航迹、爆炸地点、拦截动态或防空系统位置的频道：这类内容不是官方发布的避险预警，而是可被用于校正后续打击的实时军事情报，且对提前避险没有信息增量——官方发布的区域级警报状态与威胁类型标签已由 Tryvoha / alerts.in.ua 覆盖。该边界是数据源范围的设定，不是可开关选项。

## 自动检查更新

应用启动时（延迟约 1 秒）、从后台切回前台时、每 30 分钟自动检查版本；手动检查只在底部「软件更新」页的「立即检查更新」按钮。主页的刷新按钮不参与版本检查，避免把「刷新数据」和「检查软件更新」混在一个动作里。自动触发受 5 分钟节流约束，只有检查成功才占用节流，不会随数据轮询重复请求。检查同时读取两个来源：数据快照里的 `app` 版本信息（与页面数据同一个地址，最不易被手机网络阻断）和公开仓库的 `releases/latest`，取其中最高的版本；任一来源可用即可工作。两条路径都不需要令牌，也都位于 GitHub，手机不连接本机服务。

每次检查的结果都会显示在页面顶部的常驻状态条，包括「已是最新版本 vX.Y.Z（检查时间 · 来源）」和明确的失败原因，不再出现「什么都没发生」被误判为功能失效。发现新版本时状态条提示点底部「软件更新」查看，标签上出现红点。全部来源失败时，1 分钟后自动重试，也可在「软件更新」页手动检查。1.2.0 及更早版本只依赖 `api.github.com` 直连并回退到电脑地址，两者在手机上都不稳定，且结果只写在设置页、失败后 5 分钟内不再尝试，这是旧版更新功能表现不可靠的原因。

APK 内与浏览器内的当前版本都是编译期写入 `www/app.js` 的 `BUILD_VERSION`，不依赖服务端返回值，因此不会被新版本的服务端或 Service Worker 缓存反向覆盖。页面资源更新由 Service Worker 单独提示「点击刷新」，不静默重载页面。

发现更高版本时，页面顶部状态条显示检查结果并给出「查看更新」入口，底部「软件更新」标签出现红点；打开该页后显示蓝色更新卡片，含新版本号、来源、更新说明与安装包大小，提供「下载更新」「稍后」「忽略此版本」三个操作。已授权浏览器通知时还会发一条与警报无关的版本提示。「忽略此版本」写入本地存储，之后不再自动提示，但「软件更新」页的「取消忽略」可随时恢复，手动检查始终能看到结果。应用**只提示，不自动下载、不自动安装，也不替换 APK 内已打包的网页资源**：Android 侧载安装必须由用户确认，覆盖安装不会清除已保存的设置。

需要特别注意：v1.0.0 及更早的安装包内没有更新检查代码，必须先手动安装一次 1.1.0 或更高版本，之后才能收到自动更新提示。这条限制无法通过服务端改动绕过。

发布新版本时，修改 `version.json` 的 `version`、`versionCode`（每次递增）、`releasedAt` 与 `notes`，执行 `npm run version:sync` 把版本同步到 `www/version.json`、`www/app.js`、`package.json` 与 Gradle，再执行 `npm run build:apk` 构建并更新 `dist/` 校验和，最后提交并用 `npm run publish:github` 发布同名 tag 的 Release。客户端靠 Release 的 `tag_name` 判断版本，所以 tag 必须是 `v` 加三段式版本号，资产文件名须保持 `kyiv-live-debug.apk`。

## 版本号规范

工程采用严格三段式语义化版本 `vMAJOR.MINOR.PATCH`，例如 `v1.1.0`。三段都是十进制整数，不补前导零，不附加 `-rc`、`+build`、日期或渠道后缀。这不是风格偏好：客户端按三段十进制数字比较版本，`v1.2.0-rc.1` 会被当作 `1.2.0`，而 GitHub 的 `releases/latest` 不把 prerelease 视为最新，两者叠加会出现「提示了却下载不到对应包」的状态。

| 位 | 触发条件 | 示例 |
| --- | --- | --- |
| PATCH | 数据源解析容错、文案与排版、构建脚本、依赖安全修复，以及不改变既有设置与接口契约的缺陷修复 | 1.1.1 |
| MINOR | 新增功能模块、新增官方数据源、新增设置项或界面卡片，且旧设置仍可直接沿用 | 1.2.0 |
| MAJOR | 应用标识、包名或签名变更，数据服务接口不兼容，必须重新配置才能运行，或信息边界发生根本变化 | 2.0.0 |

内容边界不可逾越，应用标识与接口契约也保持稳定，因此 MAJOR 在可预见的范围内不会使用；这不意味着可以把不兼容变更塞进 MINOR。`versionCode` 是与版本字符串一一对应的纯递增发布序号，不把三段语义编码进数字：已发布的 1.0.0 对应 1、1.1.0 对应 2、1.2.0 对应 3、1.3.0 对应 4、1.3.1 对应 5、1.3.2 对应 6、1.3.3 对应 7，下一次无论选 1.3.4 还是 1.4.0，versionCode 都是 8。Android 只允许覆盖安装更高 versionCode 的包，所以序号不得回退或复用，也不允许同一版本对应多个序号。决定下一次版本号的规则是确定的：只修问题用 1.3.4，加新功能用 1.4.0，两者都取 versionCode 8。

tag 固定为 `v` 加 `version.json` 的 `version`，Release 资产名固定 `kyiv-live-debug.apk`；不创建 prerelease，不删除已发布 Release，否则 `releases/latest` 会回退到旧版本，客户端的判断随之失真。`notes` 写一句用户可感知的变化，8 至 120 字，会同时出现在更新提示条与 Release 说明里；`releasedAt` 用 `YYYY-MM-DD`。同一版本允许重新构建或重发资产，但客户端不会提示更新，要让用户收到提示必须提升版本号。

规则由 `scripts/version-rules.mjs` 统一定义，构建与发布两端共用。`npm run version:sync` 校验格式、日期与更新说明，并读取 `git show HEAD:version.json` 与上一版对照，拒绝版本回退、拒绝 versionCode 不递增、拒绝同版本改序号；`npm run publish:github` 发布前再校验一次，并核对 `dist/SHA256SUMS.txt` 与 APK 实际 SHA-256 一致，防止改了源码却忘记重新构建就发版。客户端的 `parseVersion` 为兼容历史 tag 采用前缀匹配，因此禁止绕过脚本手工创建带后缀的 Release。

## 本地运行

需要 Node 18 以上。

```
npm install
npm start
```

浏览器访问 `http://localhost:8787` 可在本机预览页面；服务默认只监听 `127.0.0.1`，不向局域网开放，也不提供安装页或 APK 下载。手机端一律从 GitHub Release 安装 APK，并从静态快照读取数据。

APK 出厂只写入 `www/config.json` 的数据模式标记（`dataMode: github`），取数地址固定为 `SNAPSHOT_URL`，与这台电脑是否开机无关。构建脚本 `scripts/set-default-proxy.js` 不再接受 `KYIV_DATA_URL`，也不再写入任何局域网地址。旧版保存过的电脑地址与按地址查询字段会在配置迁移时清除，分组、刷新间隔与通知偏好保留。

alerts.in.ua 官方令牌的申请入口为 `https://alerts.in.ua/api-request`。取得令牌后把 `.env.example` 复制为 `.env`，填入 `ALERTS_UA_TOKEN`，重启服务，执行 `npm run check:token` 验证。令牌只保留在服务端环境变量中，不写入前端、仓库或 APK。

## 远端数据：GitHub 静态快照

默认数据源是 `https://raw.githubusercontent.com/ericljw98-crypto/kyiv-live/snapshot/status.json`。`scripts/build-snapshot.mjs` 复用 `server/sources.js` 的同一套聚合逻辑，把区域级警报状态、全部停电分组、两种供水范围的官方公告、袭击后果公开报道索引与最新版本信息写成一份约 90 KB 的静态 JSON，推送到独立的 `snapshot` 分支。客户端只读取这一个 HTTPS 地址，不需要同一 Wi-Fi，也不需要在手机上开放任何端口。

数据粒度是**约 5 分钟的快照**，不是实时接口。界面在顶部状态条与页脚显示快照生成时间与「已过 N 分钟」，不把延迟状态标成实时；超过 15 分钟未更新会转为琥珀色警示并注明「数据可能过期」。避险决策始终以实体警报器与官方空袭警报应用为准。按地址查询任意门牌的入口已从客户端移除，快照内置全部分组可直接下拉选择。`snapshot` 分支每次以单提交强制推送，不会污染 `main` 的历史。

**生成端有两层，分工是确定的。** 严格的 5 分钟由本机 Windows 计划任务 `KyivLive Snapshot Push` 承担：每 5 分钟调用 `scripts/push-snapshot.mjs`，生成并强推一份完整快照，登录时触发、错过自动补跑、并发实例忽略。日志写在 `C:\Users\user\.workbuddy\kyiv-live\snapshot-push.log`；查看状态用 `Get-ScheduledTaskInfo -TaskName 'KyivLive Snapshot Push'`，暂停与恢复分别用 `Disable-ScheduledTask` 和 `Enable-ScheduledTask`。令牌不写入仓库、配置文件或日志：计划任务运行时从环境变量或 WorkBuddy 历史会话记录取回此前提供的 classic PAT，只在本次进程及其子进程的内存中传递。

云端 `.github/workflows/snapshot.yml` 是电脑离线时的兜底，cron 错峰为 `2-57/5 * * * *`，可用 `workflow_dispatch` 手动触发，也支持可选的 `ALERTS_UA_TOKEN` secret 切换至官方警报接口。**GitHub 官方只保证 scheduled workflow 在 1 小时内触发**，整点与 5 分刻度排队更严重，本仓库实测 12 小时只触发过一次定时，因此它不能替代本机计划任务来保证 5 分钟。工作流生成后先判断：完整快照直接发布；不完整时读取线上快照年龄，10 分钟内本机刚推过就跳过，避免用降级数据覆盖完整数据；线上已陈旧则照常发布，不可用字段保持 `unavailable`，由客户端显示「暂不可用」，不拿旧值冒充实时状态。

**上游出口限制**：GitHub Actions 的出口 IP 会被 `tryvoha.online` 与 `vodokanal.kyiv.ua` 以 403 拒绝，供电公司接口通常可访问。这不是请求头问题，伪装成浏览器也无法绕过地理出口。本机推送用的 `scripts/push-snapshot.mjs` 会校验警报、停电、供水三个模块均为「正常」才强推，因此本机在线时线上始终是完整快照。手动方式为 `GITHUB_TOKEN=<classic PAT> npm run snapshot:push`（一次）或 `GITHUB_TOKEN=<classic PAT> npm run snapshot:loop`（每 5 分钟常驻）；令牌只经环境变量传入，不写入文件。

**分发侧还有一层缓存**：`raw.githubusercontent.com` 对同一路径固定缓存 5 分钟（`Cache-Control: max-age=300`），且忽略查询串与 `Cache-Control: no-cache` 请求头，客户端 `snapshotFetchUrl()` 的 `_t` 时间戳只能绕过浏览器自身缓存，绕不过这层边缘缓存。因此手机看到的快照最多比最新推送滞后一个周期，页面已用生成时间与过期提示如实标注。要完全消除这一层只能改用 GitHub Contents API 等动态地址，但会引入匿名速率限制并需要升级 APK，而 5 分钟的粒度与当前方案相当，故不做此替换。

因此数据链路是确定的：手机在任何网络都能打开并读到最后一份数据，电脑只影响数据新鲜度，且只负责生成并推送快照。要完全脱离本机又保持数据新鲜，唯一可靠路径是把 `server/sources.js` 的聚合逻辑部署到出口 IP 能访问三个上游的云主机或边缘函数，由它把结果写入同一静态地址；服务端已支持 `HOST`、`PORT`、CORS 与可选的 `ALERTS_UA_TOKEN`，迁移不需要改 APK，也不影响更新检查。仓库不保存任何云平台凭据。

## 构建 APK

需要 JDK 17 以上与 Android SDK（compileSdk 36），并设置 `JAVA_HOME`、`ANDROID_HOME`。

```
npm run setup:android   # 首次生成 android/ 工程
npm run version:sync    # 改动 version.json 后同步版本（build:apk 内也会自动执行）
npm run build:apk       # 生成 kyiv-live-debug.apk 并刷新 dist/ 校验和
```

Windows 下也可直接运行 `scripts\build-apk.bat`。产物为 debug 签名，包名 `app.kyivlive.board`，minSdk 24、targetSdk 36。安装命令：`adb install -r kyiv-live-debug.apk`。

## 发布到 GitHub

发布脚本为 `scripts/publish-github.mjs`，零第三方依赖。它读取环境变量 `GITHUB_TOKEN`，校验令牌所属账号，创建或复用 `ericljw98-crypto/kyiv-live` 仓库，推送当前提交，按 `version.json` 的版本号创建 `v<版本>` Release 并上传 APK 资产，Release 说明会自动带上 `notes`。客户端的更新检查正是读取这个 Release，因此发布成功后手机上才会出现更新提示。令牌不会写入仓库、日志或任何配置文件。

```
GITHUB_TOKEN=<personal access token> npm run publish:github
```

所需令牌推荐 classic PAT（`ghp_` 开头，勾选 `repo`）。若使用 fine-grained token（`github_pat_` 开头），除 `Contents: Read and write` 外，还必须在 Account permissions 中把 `Repository creation` 设为 Read and write，否则 `POST /user/repos` 会返回 403；也可以在 `https://github.com/new` 手动创建名为 `kyiv-live` 的空仓库（不要初始化 README），脚本会自动复用并继续推送与发布。

脚本默认创建**私有仓库**，加 `--public` 参数可创建公开仓库或把已有私有仓库改为公开。`github.com/ericljw98-crypto/kyiv-live` 当前为**公开仓库**，Release 的 APK 可免登录直接下载，手机浏览器打开下载链接即可安装；更新检查接口对公开仓库同样免令牌。脚本只会把私有改为公开，不会反向改回；如需恢复私有，在仓库 `Settings → General → Danger Zone → Change visibility` 操作，或用 API `PATCH /repos/ericljw98-crypto/kyiv-live` 提交 `{"private": true}`。

公开会带来一项不可逆的影响：源码与 git 历史中包含默认关注地址（志愿营街 44A 号、佩切尔斯基区；官方地址库匹配所需的乌克兰语原名保存在 `server/sources.js` 的关键词表中），涉及 `server/sources.js`、`www/app.js`、`www/index.html`。仓库转为公开后，这些信息可被搜索引擎与爬虫抓取，即使随后改回私有也无法撤回已产生的副本。若需脱敏，应把默认地址改为运行时填写、清理历史提交并重新构建 APK，而不是仅删除当前版本的文件。

## 目录

```
version.json  版本真源，由 npm run version:sync 同步到各编译产物
server/    零依赖 Node 代理与数据聚合、缓存、区域筛选、/api/update 更新接口
www/       PWA 前端、图标、manifest、service worker、版本描述
scripts/   快照生成、图标生成、Android 补丁、构建与发布脚本
.github/   Actions 工作流：电脑离线时兜底生成并发布静态数据快照
android/   Capacitor 生成的 Android 工程
dist/      已编译 APK 与 SHA-256 校验和
```
